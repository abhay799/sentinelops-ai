# Phase B — Failure Prediction Evaluation & Hardening

**Step:** B0 — methodology definition and freeze
**Status:** FROZEN BEFORE PHASE B EXPERIMENTS
**Scope:** local/synthetic research evaluation only
**Parent:** Phase A completed as CERTIFIED WITH CAVEATS

## 1. Objective

Phase B asks:

> Can SentinelOps issue a useful failure warning before a failure begins, using only information available at prediction time, under a chronology-safe evaluation protocol?

The existing Phase 10 implementation is the starting baseline only. No Phase B registered result may be produced until chronology, label, detector-fit, split, threshold, and lead-time gates pass.

## 2. Existing baseline

Current implementation:
- `configs/failure_prediction.yaml`
- `scripts/build_phase10_early_warning.py`
- `scripts/train_phase10_predictor.py`
- `src/sentinelops/prediction/early_warning.py`
- `src/sentinelops/prediction/evaluation.py`
- `scripts/train_phase5_anomaly.py`
- `tests/test_phase10_early_warning.py`

Current behavior:
- lookahead horizon: 3 future service observations
- minimum history: 3 observations
- history window: 20 observations
- heuristic threshold: 0.55
- supervised model: logistic regression
- model random state: 42
- supervised decision threshold: 0.5
- label: `future_anomaly`
- lead proxy: `lead_events`

The current tests show an important point-in-time property: changing a future latency value does not change an earlier warning score.

## 3. Baseline integrity findings

### B0-F1 — upstream detector fit leakage risk

`scripts/train_phase5_anomaly.py` fits Isolation Forest on the full temporal feature matrix and scores that same matrix. Its outputs contribute to `is_anomaly`, later used to construct `future_anomaly`.

**Rule:** registered Phase B evaluation must not use labels generated by a detector fitted on validation/test future observations.

### B0-F2 — label-aware split selection

`choose_temporal_split()` tests fractions 0.60, 0.65, 0.70, 0.75, 0.80 and selects a boundary after inspecting label distributions, including whether TEST contains positives. The configured `train_fraction: 0.70` is not the controlling split.

**Rule:** registered partition boundaries must be selected without inspecting validation/test labels.

### B0-F3 — no true wall-clock lead time yet

The current pipeline has `feature_as_of_time`, `future_anomaly`, and `lead_events`, but no independent ground-truth fault injection/onset timestamp preserved for each failure episode.

**Rule:** wall-clock lead-time claims require a frozen onset timestamp source independent of the predictor.

### B0-F4 — threshold not yet justified

The heuristic threshold is 0.55 and supervised predictions use 0.5. Neither is selected under a frozen Phase B validation-only objective.

**Rule:** final operating thresholds must be selected on TRAIN/VALIDATION only and frozen before TEST scoring.

## 4. Evaluation unit

Primary unit: a **failure episode**, not an arbitrary telemetry row.

Each episode must include:
- `episode_id`
- service
- fault/scenario type
- run/seed identifier
- observation timestamps
- failure onset timestamp
- failure end/reset timestamp where available
- feature-as-of timestamps
- prediction scores
- detector provenance
- TRAIN / VALIDATION / TEST partition

Rows from the same episode may not cross partitions.

## 5. Prediction target

Primary target:

> predict whether a registered failure episode will begin within the frozen prediction horizon, before failure onset.

Two horizons:
1. event horizon: current 3-observation lookahead
2. wall-clock horizon: only after stable cadence and onset timestamps are established

If trustworthy wall-clock evidence cannot be built, Phase B reports event-based lead only and marks wall-clock lead unavailable.

A prediction at or after failure onset is not an early warning.

## 6. Leakage invariants

For prediction time `t`:
- every feature must have `feature_as_of_time <= t`
- no feature may use telemetry after `t`
- no normalization/statistic may be fitted using validation/test future values
- learned upstream detectors used by predictor inputs/labels must be TRAIN-only or causal/stateless
- TEST labels cannot influence split, features, model, threshold, scorer, or analysis

Required invariance tests:
1. mutate future telemetry; earlier features/scores remain identical
2. mutate TEST labels; split boundary remains identical
3. mutate TEST features; TRAIN-fitted model/preprocessing artifacts remain identical
4. every counted warning timestamp is strictly before onset

Any violation is a stop condition.

## 7. Partition policy

Chronological and episode-grouped:
- TRAIN: first 60%
- VALIDATION: next 20%
- TEST: final 20%

Fractions are computed over chronologically ordered episode groups.

Exact episode IDs/boundaries must be written to a manifest and hashed before model evaluation.

If chronology plus sufficient positive/negative support cannot be preserved, Phase B stops as **insufficient evaluation data**. The split is not silently moved.

## 8. Detector/preprocessing fit policy

All learned state obeys the same chronology boundary:
- Isolation Forest
- normalization/scaling
- imputation statistics
- feature selection
- calibration
- threshold selection
- learned temporal baselines

TRAIN fits state. VALIDATION may select among preregistered choices. TEST is evaluation only.

Phase B v1 does not refit on TRAIN+VALIDATION before the registered TEST result.

## 9. Models

Phase B v1:
1. Heuristic v1 — existing weighted early-warning score
2. Supervised v1 — logistic regression with:
   - latency warning component
   - error warning component
   - request warning component
   - change warning component
   - history event count

Baselines:
- prevalence / constant-risk baseline
- random baseline with frozen seed 42 where thresholded comparison is meaningful

No new feature is added after validation/test outcomes are visible.

## 10. Threshold selection

TEST is never used for threshold selection.

For each continuous score:
1. fit on TRAIN
2. score VALIDATION
3. build full precision-recall curve
4. evaluate thresholds from unique VALIDATION scores
5. maximize frozen utility
6. ties choose the higher threshold

Frozen utility:

`utility = 2 * TP - 1 * FP - 3 * FN`

This is an experimental research utility, not an externally validated production cost model.

Selected thresholds must be frozen before TEST scoring.

## 11. Primary metrics

Registered TEST metrics:
- precision
- recall
- F1
- PR-AUC / Average Precision
- false-positive rate
- TP / FP / TN / FN
- positive-episode warning coverage
- median lead time
- mean lead time
- p25 / p75 lead time
- fraction of positive episodes warned at least one observation before onset

If wall-clock onset is trustworthy, lead time is reported in seconds and event offsets. Otherwise event offsets only.

ROC-AUC is secondary.

## 12. PR and calibration evidence

Required:
- precision-recall curve
- threshold table
- score distributions by class
- calibration/reliability table where sample size supports it

A single F1 point estimate is insufficient for certification.

## 13. Confidence intervals

Registered TEST uncertainty:
- seed 42
- 10,000 bootstrap resamples
- 95% percentile interval
- resampling unit: failure episode

At minimum:
- precision
- recall
- F1
- Average Precision
- warning coverage
- median lead time where defined

Paired model differences reuse the same bootstrap episode indices.

## 14. Lead-time rule

A true-positive warning contributes lead time only when:
- score crosses frozen threshold
- episode is positive
- warning timestamp < failure onset

Primary episode lead time:

> failure onset timestamp minus earliest qualifying warning timestamp within the frozen horizon.

Repeated warnings within one episode create one primary sample.

## 15. Required final analyses

- overall TEST metrics
- PR curve and threshold-selection evidence
- chronological partition manifest
- leakage audit
- lead-time distribution
- per-fault metrics where support is sufficient
- per-service diagnostics as secondary evidence
- confusion counts
- calibration diagnostics
- paired heuristic-vs-supervised differences
- prevalence/no-skill comparison
- false-positive / false-negative analysis

Small subgroup tables are descriptive only and cannot drive tuning.

## 16. Acceptance gates

### Mandatory integrity gates
- zero known future-feature leakage
- zero label-aware TEST split selection
- upstream learned detector/preprocessing fit without TEST future
- validation-only threshold selection
- scorer frozen before TEST
- episode-grouped chronological split
- no post-TEST outcome-driven tuning
- reproducible seeds/hashes

Failure of any integrity gate => **NOT CERTIFIED**.

### Predictive evidence gates
Because the repository has no externally justified production cost target, Phase B v1 does not freeze an arbitrary product-readiness F1 threshold.

Certification requires:
- Average Precision above TEST prevalence/no-skill baseline
- positive warning coverage on TEST
- at least one true-positive episode warned strictly before onset
- reported precision, recall, F1, and lead-time uncertainty
- no production-readiness claim

If evidence passes but sample size is limited or CIs are wide => **CERTIFIED WITH CAVEATS**.

## 17. Stop conditions

Stop before TEST scoring if:
- TEST labels influenced split/model/features/threshold
- upstream detector used TEST future during fit
- wall-clock lead is claimed without independent onset timestamps
- partition overlap exists
- scorer changed after TEST outcome inspection
- episode manifest/hash is missing

After TEST scoring, tuning requires a new versioned protocol and a new held-out TEST set.
